# ML-ядро: прогноз выработки ВЭС на 24–48 ч

## Запуск

```bash
py -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python train.py                      # CV по трём месяцам + финальные модели -> artifacts/
.venv\Scripts\python predict.py                    # replay февраля -> forecasts/ (всё или ничего)
.venv\Scripts\python scripts\check_replay.py       # критерии приёмки (26 проверок)
.venv\Scripts\python scripts\check_time_alignment.py
.venv\Scripts\python scripts\check_publication_delay.py
```

`predict.py` сначала собирает все 28 выпусков в памяти. Если хоть один не собран, скрипт завершается с кодом 1, перечисляет выпуски и часы без погоды, а предыдущие прогнозы не трогает. Новый комплект подменяет старый только целиком.

Погода закэширована в `data/cache/` вместе с JSON (endpoint, параметры, узел сетки, `retrieved_at`, `sha256` ответа), поэтому replay воспроизводится без сети. `load_weather(t, refresh=True)` скачивает заново.

## Время

| Понятие | Значение |
|---|---|
| Внутри пайплайна | naive UTC |
| Часы SCADA (CSV и выходные прогнозы) | фиксированный UTC+6 |
| Выпуск прогноза (`issue_time`) | 23:00 по часам SCADA = 17:00 UTC, ежедневно с 31.01 по 27.02 |
| Горизонт | 48 ч: сутки D+1 и D+2 по часам SCADA |
| Час H | среднее 10-минутных записей H:00..H:50, не меньше 4 из 6 |

Часы SCADA определены по данным, а не по допущению. Корреляция 10-минутного ветра турбин с ветром NWP (UTC) максимальна при сдвиге +6 ч во всех периодах, в том числе после перехода Казахстана на UTC+5 1 марта 2024 года (`scripts/check_time_alignment.py`). Значит, CSV ведётся по фиксированному UTC+6. Прогнозы выдаются в тех же часах, чтобы совпасть со скрытым февральским фактом.

## Погода, доступная на момент выпуска

Источник: Open-Meteo **Previous Runs API**, переменные `wind_speed_100m_previous_dayN` и `temperature_2m_previous_dayN`. Это значение для часа прогноза из запуска, сделанного на N суток раньше.

Для каждого прогнозного часа берётся свежайший запуск, который гарантированно опубликован до `issue_time`:

```
N = ceil((lead_hours + 12) / 24)     # 12 ч — задержка от инициализации до публикации
lead 1–12 ч -> previous_day1,  13–36 ч -> previous_day2,  37–48 ч -> previous_day3
```

Если нужного запуска в архиве нет, берётся более старый: он опубликован ещё раньше, значит тоже допустим. Колонка `run_day` показывает, какой запуск использован.

Откуда 12 ч. Задержка от инициализации до доступности на Open-Meteo измерена через metadata API (`scripts/check_publication_delay.py`, результат в `data/cache/model_publication_delays.json`):

| Модель | Задержка |
|---|---:|
| DWD ICON | 3.8 ч |
| NCEP GFS | 5.5–6.5 ч |
| CMA GRAPES | 6.3 ч |
| ECMWF IFS HRES / 0.25° | 7.0 / 7.8 ч |
| JMA GSM | 9.6 ч |

Previous Runs отдаёт `best_match`, и неизвестно, какую из моделей он берёт для этой точки. Поэтому задержка выбрана так, чтобы покрыть самую медленную модель с запасом 2.4 ч. Замер относится к текущим запускам (сентябрь 2026), а не к историческим. Задержки публикации стабильны, но это остаётся допущением.

Historical Forecast API не используется. Он склеивает первые часы последовательных запусков, и выпуск от 1 февраля получал бы погоду из запусков 2–3 февраля. Архив `previous_dayN` начинается 16.02.2024, поэтому обучение идёт с этой даты.

Обе турбины попадают в один узел сетки (43.620, 78.479), примерно в 5 км от турбин.

## Модель

1. **Level 1** — эмпирическая кривая мощности по ветру с поправкой на плотность воздуха (IEC 61400-12): медиана нормированной мощности в корзинах по 0.5 м/с, монотонная. Обучается на **прогнозном** ветре, который модель получает на инференсе, а не на анемометре турбины. Паспортных характеристик турбин нет, поэтому это не паспортная кривая.
2. **Level 2** — LightGBM (L1). Два варианта: `residual` (учит поправку к Level 1, с весом смешивания) и `direct` (учит мощность, Level 1 — один из признаков).

Признаки только погодные: `wind_fc`, `temp_fc`, плотность, скорректированный ветер, Level 1 и его сглаживание по соседним часам, соседние часы прогноза, рампа, `run_day`, `lead_hours`, час/день недели/месяц. Лаги SCADA считаются для baseline и валидатора, но в модель не входят: в феврале фактов нет, и replay не должен от них зависеть.

## Валидация

- Три скользящих фолда по целевому времени: ноябрь 2025, декабрь 2025, январь 2026.
- Внутри фолда: fit → inner (30 дней, early stopping и вес смешивания) → evaluation. Выпуск попадает в сегмент, только если все его 48 целевых часов внутри сегмента, поэтому метки не пересекают границы.
- Метка часа H закрывается в H+1ч (это среднее H:00..H:50). В fit, inner и evaluation остаются только метки, закрытые к первому выпуску следующего сегмента. Для evaluation это важно, потому что его оценки выбирают вариант модели, а выбор делается до первого февральского выпуска.
- Кривая мощности обучается только на fit-части.
- Правило выбора зафиксировано заранее: минимальный средний MAE по фолдам.
- Финальная модель обучается на всей истории с числом итераций и весом, выбранными в CV. Последняя метка — 31.01.2026 16:00 UTC: она закрывается ровно в момент первого выпуска (17:00 UTC).

## Результаты (среднее по трём фолдам, нормированная мощность)

| Турбина | Модель | MAE | RMSE |
|---|---|---:|---:|
| 1 | Level 1 (кривая) | 0.1898 | 0.2658 |
| 1 | residual | 0.1795 | 0.2557 |
| 1 | **direct** (выбрана) | **0.1785** | 0.2567 |
| 2 | Level 1 (кривая) | 0.1900 | 0.2678 |
| 2 | residual | 0.1765 | 0.2576 |
| 2 | **direct** (выбрана) | **0.1760** | 0.2571 |

Persistence (последний известный час) даёт MAE 0.34–0.38. Он возможен только в эксплуатации со свежей SCADA и приведён для масштаба. ML-слой выигрывает у кривой во всех трёх фолдах у обеих турбин (−6.0% и −7.4% MAE). На горизонте 25–48 ч ошибка выше, чем на 1–24 ч. Метрики по фолдам и lead-корзинам — в `artifacts/manifest_t*.json`.

В каждом фолде около 1 400 пар (issue, target), но только около 740 уникальных целевых часов: соседние выпуски перекрываются, поэтому это не 1 400 независимых наблюдений.

```python
from src.data import load_turbine_hourly
from src.weather import load_weather, weather_snapshot, weather_provenance

history = load_turbine_hourly(turbine_id)          # UTC-индекс

artifacts = load_artifacts(turbine_id)             # + artifacts["manifest"]["model_version"]

    forecast = run_forecast_model(history, weather, issue, artifacts)

```

`forecast`: индекс `time_utc`; колонки `time_scada`, `lead_hours`, `prediction`, `level1` (референс для валидатора), `residual_pred`, `wind_fc`, `temp_fc`, `run_day` (из какого запуска погода — для лога агента).

Изменения относительно WIP-коммита: `fetch_archived_forecast` заменена на `fetch_previous_runs` + `weather_snapshot`; `load_weather(t)` вызывается без дат; файлы артефактов переименованы; индекс прогноза в UTC.
